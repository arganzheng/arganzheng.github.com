## 内容简介

《产品与体验：把不确定的能力做成可信的产品》是一组共五篇的系列文章，是[《AI 应用工程师学习地图》](/ai-application-engineer-learning-roadmap.html)第七层（L7）的正文，也是应用地图的最后一个系列。前六层把一个 AI 应用从模型组件到生产运营搭了起来；这一层回到起点的问题：**这个能力该做成什么产品、给谁、以什么形态、让人怎么信任它、怎么知道它有用**。

这一层的特殊性只有一条，但它决定一切：**产品里有一个会出错、且不知道自己什么时候出错的组件**（L1 第一篇）。传统产品的功能要么对要么坏，AI 产品的功能是"多数时候对、有时错、错得很自然"。于是场景选择要问"错了代价多大、能不能被发现"；形态选择要问"人在哪一步看结果"；信任要被**校准**而不是最大化——过度信任让用户把错误当真（Air Canada 的乘客、引用虚构判例的律师），信任不足让功能没人用；不确定性要被**呈现**而不是隐藏；指标要量"真的有用"而不是"用了多少"。

2024–2026 年的公开案例给了这一层足够的教材。**Klarna** 2024 年宣布 AI 客服做了 700 个人的工作、解决三分之二的工单、把处理时间从 11 分钟压到 2 分钟；2025 年 CEO 承认裁得太狠、复杂与情绪化的问题 AI 处理不了、客户要能找到人；到 2026 年变成混合模式——AI 做第一响应、人处理例外与挽留。**Duolingo** 2025 年 4 月宣布"AI-first、逐步停用 AI 能做的合同工"，一周后 CEO 改口"AI 不是替代员工"。**Gartner** 2026 年预测被 AI 裁掉的岗位三成会在 2029 年前补回、成本更高。哈佛与 BCG 对 758 名顾问的实验给了这些故事的结构：在 AI 擅长的任务边界内快 25%、质量高 40%，边界外用 AI 的人出错率反而高 19 个百分点——**"锯齿状边界"**：同一个工作流里相邻的两个任务，一个 AI 碾压、一个 AI 拖累。产品设计的核心工作就是找到这条边界，把 AI 放在边界内、把人放在边界上。

它回答的问题是：

> **哪些场景该做 AI 产品、哪些不该，demo 与产品之间的鸿沟是什么？copilot、agent、自动化三种形态怎么选，2026 年为什么后台 agent 成了主流？人机分工怎么定、信任怎么校准？不确定性怎么呈现、非对话形态有哪些？产品指标量什么、怎么回流到系统？**

五篇沿一条线走。**第一篇**场景选择：四个维度（价值、可验证性、错误容忍度、频率）与锯齿状边界；Klarna、Duolingo、IBM 的回撤与它们共同的错误（把"简单查询上的 700 人"外推到全部客服）；GitHub Copilot 从补全到 agent 的十年为什么成立（代码可验证、错误可撤销、高频）；demo–产品鸿沟的五个来源（分布、长尾、集成、信任、成本）；"80% 的 demo 是 20% 的产品"。**第二篇**形态：copilot（人主导、AI 建议）→ agent（AI 主导、人监督）→ 自动化（无人在环）的梯子，与 L4 第八篇六级人机分工的产品侧对应；2024–2026 年的形态演进——补全 → 对话 → 编辑器内 agent → **后台 agent**（Codex cloud、Claude Code on the web、Cursor 后台 agent、Devin：提任务、走开、回来审 PR），为什么它成了主流（异步交付把等待变成了并行、PR 是天然的审阅落点）；按任务选形态的决策表；同一产品里多形态并存。**第三篇**人机分工与信任校准：过度信任（自动化偏见——人不再核对）与信任不足（有功能没人用）都是失败；采纳率与修改率的公开数据（Copilot 建议接受率约三成、多数被接受的建议被再编辑）说明"人在编辑"是常态而不是失败；校准的手段——显示依据与来源、显示不确定性、可撤销、可核对的呈现、期望管理、渐进的自主性（先 copilot 后 agent）；把"绕过障碍"与"不确定"作为需要人介入的信号推给用户（L4 第八篇）；onboarding 里教用户 AI 不擅长什么。**第四篇**不确定性的呈现与非对话形态：引用与来源（可点开、定位到原文——L3 与 L5 的引用正确率在这里有产品意义）、置信度怎么呈现（不给原始分数、用行为表达：直接给 / 给几个候选 / 问人）、拒答的呈现（说缺什么、下一步能做什么，而不是"无法回答"）、流式与进度（L6 第三篇的感知延迟）、agent 步骤的可视化（DeepSeek Harness 的 Trajectory 视图、Codex 与 Claude Code 的步骤流）、审批的交互（L4 第五篇的 `justification` 与影响范围）、diff 式审阅（PR、变更预览）；非对话形态——内联建议、按钮化的动作、环境感知（在用户的工作流里而不是另一个窗口）、生成式 UI、语音与实时；对话不是默认。**第五篇**产品指标与回流：采纳率、修改率、任务完成率、时间节省（自报 vs 实测的差距）、留存、升级率（转人工、放弃）、CSAT、每任务成本 vs 价值（L6 第二篇）；北极星怎么选；反指标（消息数、"AI 用量"一类的虚荣指标）；定性研究（看用户怎么用、怎么绕过）；指标回流到飞轮（L6 第七篇）与评测集（L5）；A/B 在 AI 产品里的特殊性。

系列的组织原则：**每一篇都以"这个组件会出错"为前提**。场景选边界内的、形态让人在合适的位置、信任校准到与实际能力一致、不确定性诚实呈现、指标量真实价值——五篇是同一个前提的五个推论。


## 为什么写这个系列？

### 技术对了，产品可以照样失败

前六层的失败分类里有一类"技术上正确、用户不想要"（L5 第六篇）。Klarna 的 AI 在简单查询上真的做得好，失败在把它放到了边界外；Duolingo 的翻译 AI 可能真的够用，失败在沟通与信任。很多团队把前六层做扎实了，产品还是没人用或用了就出事——问题在这一层。

### 回撤的年份

2025–2026 年是 AI 产品**回撤**的年份：Klarna、IBM（AskHR 替代 HR 后又招人）、Duolingo 改口、Gartner 预测三成岗位补回。这些不是 AI 不行的证据，是**边界判断错误**的证据——用边界内的数字外推到全部。这一层要给出判断边界的方法。

### 形态在变

2024 年的 AI 产品形态是对话框；2026 年 coding 领域的主流是后台 agent——提任务、走开、回来审 PR。这不只是 coding 的事：任何有天然审阅落点（PR、草稿、提案）的任务都在往这个形态走，L4 第八篇的"人在环上"在产品侧就是它。形态选错，同样的能力体验差一个量级。

### 现有材料的断层

- **产品方法论**（PM 的书）不讲"组件会出错"这个前提下的设计；
- **AI UX 指南**（各大厂的设计准则）讲呈现原则，很少与前六层的工程机制（引用正确率、拒答出口、审批的 justification）接起来；
- **案例报道**讲回撤，不讲判断边界的方法；
- **指标文章**多停在采纳率，不讲自报与实测的差距、不讲回流。

本系列想填补的是从"能做出一个 AI 功能"到"知道该不该做、做成什么形态、让人怎么信、怎么量它有没有用、怎么让它随使用变好"之间的那段路。

## 系列的整体主线

| 篇 | 主题 | 建立的东西 | 前提的推论 |
|---|---|---|---|
| 1 | 场景选择 | 四维度、锯齿状边界、回撤案例的共同错误、鸿沟五来源 | 组件会出错 → 选错了代价小、能被发现的场景 |
| 2 | 形态 | copilot → agent → 自动化的梯子、后台 agent 的兴起、决策表 | 组件会出错 → 人要在合适的位置看结果 |
| 3 | 信任 | 过度 / 不足两种失败、采纳与修改数据、校准手段 | 组件会出错 → 信任要与实际能力一致 |
| 4 | 呈现 | 引用、置信度、拒答、进度、步骤、审批、diff；非对话形态 | 组件会出错 → 不确定性要诚实呈现 |
| 5 | 指标 | 真实价值的指标、反指标、自报 vs 实测、回流 | 组件会出错 → 量"有用"而不是"用了" |

两条贯穿的线：

- **边界。** 找到 AI 擅长与不擅长的任务边界，把 AI 放在边界内、人放在边界上；边界会随模型移动，所以要持续量（第五篇）。
- **诚实。** 呈现依据、呈现不确定、呈现"我不知道"、呈现"这一步需要你"——校准信任的唯一方法是让用户看到真实的能力。


## 章节结构与分章导读

### 1. 场景选择：锯齿状边界与 demo–产品鸿沟

> 核心问题：**哪些场景该做、哪些不该？回撤的案例共同错在哪？demo 与产品之间隔着什么？**

四个维度：**价值**（每任务节省的时间 / 带来的收益——L6 第二篇的单位经济学）、**可验证性**（用户或系统能不能快速判断输出对不对：代码有测试、翻译要懂两种语言才能判、法律意见普通人判不了）、**错误容忍度**（错一次的代价：一句改错的文案 vs 一笔退错的钱 vs 一条错的医疗建议）、**频率**（高频任务的小改进累积成大价值，低频任务的学习成本抵消收益）。锯齿状边界：哈佛与 BCG 的 758 名顾问实验——边界内快 25%、质量高 40%，边界外出错率高 19 个百分点；边界不按"领域"划、按"任务"划，同一工作流里相邻任务可能一内一外。回撤案例的共同错误：**用边界内的数字外推到全部**——Klarna 的"700 人"来自简单查询，20–30% 的任务是例外（复杂争议、欺诈、政策例外、情绪化客户），外推后成本从例外处漏回来；IBM 的 AskHR 做了常规问答但做不了需要判断的；Duolingo 的问题是沟通与信任而不是能力。成功的对照：GitHub Copilot 十年从补全到 agent——代码可验证（编译、测试）、错误可撤销（git）、高频（每分钟）、人在编辑器里就在边界上。demo–产品鸿沟的五个来源：**分布**（demo 用的是精选输入，产品面对长尾——L5 第一篇）、**长尾**（80% 的情形 demo 就能做，剩下 20% 是产品的全部工作）、**集成**（demo 是一个对话框，产品要进用户的工作流、权限、数据）、**信任**（demo 不需要用户信任，产品需要）、**成本**（demo 不算钱，产品要算每任务成本 vs 价值）。决策：先把任务拆到能判断边界的粒度，边界内的做、边界上的人机分工、边界外的不做或只做辅助。

### 2. 形态：copilot、agent 与自动化——后台 agent 为什么成了主流

> 核心问题：**三种形态怎么选？2024–2026 年形态怎么演进的，后台 agent 为什么成了主流？同一产品怎么多形态并存？**

梯子：**copilot**（人主导、AI 建议、人逐条接受——补全、对话里的建议、草稿）→ **agent**（AI 主导执行、人监督——编辑器内的多步修改、审批门、结果审阅）→ **自动化**（无人在环，有退路——L4 第八篇的第六级）。它是 L4 六级人机分工的产品侧：每升一级把哪类验证交给系统（L4 第八篇的判据"能自动验证到什么程度就能自主到什么程度"）。演进：2021–2023 补全（Copilot）→ 2023–2024 对话（ChatGPT 形态进产品）→ 2024–2025 编辑器内 agent（Cursor Composer、Claude Code、Codex CLI）→ 2025–2026 **后台 agent**（Codex cloud、Claude Code on the web、Cursor 后台 agent、Devin、Agents API 的"跑几天的 agent"）：提任务、走开、回来审 PR。为什么它成了主流：**异步交付**把用户的等待变成并行（L6 第三篇的感知延迟归零）、**PR / 草稿 / 提案是天然的审阅落点**（L4 第八篇的可审阅中间物——人在环上有地方站）、模型能力到了能独立跑几十步的水平、成本随任务价值可接受（L6 第二篇）。决策表：任务粒度小且高频 → copilot（补全、内联建议）；任务有明确验收且可撤销 → agent（编辑器内或后台）；任务可自动验证且可回滚、错误代价低 → 自动化；任务边界外 → 只做辅助或不做。同一产品多形态并存（Cursor：Tab 补全 + 对话 + Composer agent + 后台 agent），按任务切换；形态的切换点是产品设计的核心决策。业务侧的对应：客服的"AI 先答、人处理例外"（Klarna 的混合模式）是 copilot 与 agent 的并存；本体驱动的业务 agent 的"提案先于落库"是后台 agent 的业务版。

### 3. 人机分工与信任校准

> 核心问题：**过度信任与信任不足各怎么发生？采纳与修改的数据说明什么？校准信任的手段有哪些？**

两种失败：**过度信任**（自动化偏见——人不再核对，把错误当真：Air Canada 的乘客信了错误的退票政策、律师提交了虚构的判例、PocketOS 的开发者没看 agent 要执行什么——L1 第一篇）与**信任不足**（功能做出来没人用、或用户每条都重做——价值归零）。校准的目标是**信任与实际能力一致**：AI 擅长的地方用户放手、不擅长的地方用户核对。数据：GitHub Copilot 的建议接受率长期在三成左右，被接受的建议多数会被再编辑——"人在编辑"是正常状态，采纳率 30% 不是失败（每分钟省几秒累积起来是真实价值），100% 才是危险信号（没人看了）。校准的手段：**显示依据**（引用、来源、"因为你之前说过…"——L3 的引用正确率、L4 第八篇记忆的来源）；**显示不确定**（第四篇）；**可撤销**（undo、git、草稿——让"信错了"的代价低）；**可核对的呈现**（diff 而不是整段替换、结构化而不是一段话）；**期望管理**（onboarding 里说清擅长与不擅长、首次使用的引导任务选边界内的）；**渐进的自主性**（新用户先 copilot、建立信任后开 agent——个人层面的六级爬梯）；**把信号推给用户**（agent 遇到障碍要绕过、不确定、要做不可逆动作时明确说"这一步需要你"——L4 第八篇的问人是产品事件而不只是运行时事件）。反过来的手段——让不信任的用户开始用：从低风险、高频、可验证的任务切入；展示成功案例；让第一次体验在边界内。信任的动态：模型升级后能力变了，用户的信任要重新校准——发布说明要说清变了什么（L6 第六篇）。

### 4. 不确定性的呈现与非对话形态

> 核心问题：**引用、置信度、拒答、进度、步骤、审批、diff 各怎么呈现？对话为什么不该是默认形态，非对话形态有哪些？**

呈现的原则：**诚实、可核对、可行动**。**引用与来源**：每个事实断言可点开定位到原文（L3 的引用正确率在这里是产品指标）；没有依据的断言不呈现为事实（L5 第七篇）。**置信度**：不给原始分数（用户无法解读且模型的分数不可靠——L5 第七篇），用**行为**表达——确定时直接给、不确定时给几个候选并说差别、很不确定时问人或说不知道；用语言而不是数字。**拒答**：说缺什么（"你的问题里没有订单号"）、下一步能做什么（"提供订单号或我帮你查最近的订单"）、而不是"无法回答"（L2 第三篇的出口在这里落地）。**流式与进度**：首字前的骨架与已知信息、token 流、步骤流、进度与预估（L6 第三篇）。**agent 步骤的可视化**：用户能看到 agent 在做什么、为什么（DeepSeek Harness 的 Trajectory 视图按来源检视每条记录，Codex 与 Claude Code 的步骤流）——透明是信任校准的手段也是调试的入口；但要分层（默认摘要、可展开细节），否则是噪声。**审批的交互**：为什么要问（`justification`）、影响范围（会改哪些文件、会调哪个外部系统、能不能撤销）、批一类的选项（L4 第五篇的审批疲劳）。**diff 式审阅**：变更以 diff 呈现（代码、文档、配置、数据的前后对比）而不是整段替换——人能核对、能部分接受。**非对话形态**：对话框是 2023 年的默认，不是最好的默认——**内联建议**（在用户正在编辑的地方）、**按钮化的动作**（"总结"、"翻译"、"修复"——一次点击而不是一段 prompt）、**环境感知**（AI 在用户的工作流里而不是另一个窗口：IDE、邮件、表格、CRM 内）、**生成式 UI**（模型输出结构化数据、前端渲染成表格 / 图表 / 表单而不是一段文字——MCP Apps 是协议层的版本，L4 第二篇）、**语音与实时**（Realtime API 一类，L1 第二篇）、**后台交付**（第二篇的 PR / 草稿 / 通知）。选形态的判据：用户在哪、任务多长、输出是什么形状、要不要来回。

### 5. 产品指标与回流

> 核心问题：**量什么才是"有用"？自报与实测差多少？哪些是虚荣指标？指标怎么回流到系统？**

指标矩阵：**采纳**（功能被用的比例、周活）、**接受与修改**（建议接受率、接受后的编辑量——修改量是质量的连续信号）、**任务完成**（用户的目标达成了吗——对话式的用会话为单位，L5 第三篇）、**时间节省**（**自报 vs 实测**：用户自报的节省常高于实测——控制组实验、任务计时、或代理指标如提交频率；两个都报并说明差距）、**升级率**（转人工、放弃、重试——负信号）、**留存**（用过一次之后还用吗——AI 功能的留存曲线常比想象陡）、**满意度**（CSAT、点赞 / 点踩的比例与选择偏差）、**每任务成本 vs 价值**（L6 第二篇的单位经济学作为产品指标）、**信任指标**（核对率——用户点开引用的比例；过度信任的信号是核对率趋零而错误率不为零）。北极星：按场景选一个（客服的"一次解决率"、代码的"合并的 PR 数 × 通过率"、写作的"发出的草稿数"），其余是护栏。**反指标**：消息数、token 用量、"AI 交互次数"——用得多不等于有用（可能是用户在反复重试）；"AI 生成占比"——不是目标。**定性**：看用户怎么用（录屏、访谈）、怎么绕过（绕过是最有信息的行为——用户在告诉你边界在哪）、什么时候关掉它。**回流**：每个指标事件带 trace id（L5 第六篇），负信号进 bad case 队列，采纳与修改的对进评测集与飞轮（L6 第七篇），绕过的场景进场景边界的重新评估（第一篇）。**A/B 的特殊性**：AI 功能的 A/B 要按用户固定分组（体验不能跳变）、要等够长（学习效应）、要看留存而不只是首次采纳、要一次一个因素（L5 第四篇）。

### 6. 系列总结与通关自测

一张总表回顾五篇各自回答的问题与必记的数字，逐篇的核心结论与常见误解，贯穿全系列的几条线，然后是三段自测——判断与计算、跨篇综合、面试题——加一份"读过 / 掌握 / 能教人"的判据。

## 本系列的边界

- **不讲通用产品方法论**：用户研究、PMF、定价策略不重复；只讲"组件会出错"带来的差异。

- **不讲商业模式**：AI 产品的定价与市场属于商业；只讲每任务成本 vs 价值作为产品指标。
- **不讲组织与变革管理**：Klarna 一类回撤的组织教训（裁员与再雇）只作为边界判断的案例。

## 最终目标

读完本系列，面对一个要做或已做的 AI 功能，读者应该能够：

| 追问 | 答案来自 |
|---|---|
| 这个任务在 AI 的边界内吗？错了代价多大、能被发现吗？我在外推哪个数字？ | 第一篇 |
| 该做成 copilot、agent 还是自动化？人在哪一步看结果？该变成后台 agent 吗？ | 第二篇 |
| 用户是太信还是不信？采纳率与修改率说明什么？怎么校准？ | 第三篇 |
| 引用能点开吗？拒答说了缺什么吗？审批说了为什么吗？为什么是对话框？ | 第四篇 |
| 北极星是什么？自报的节省与实测差多少？指标回流到评测集了吗？ | 第五篇 |

这就是 L7 要建立的能力：**在"组件会出错"的前提下做产品决策**——选边界内的场景、让人在合适的位置、把信任校准到与能力一致、诚实呈现不确定、量真实的价值并让它回流。七层合起来，就是应用地图想给读者的全部：从模型组件到可信的产品。
